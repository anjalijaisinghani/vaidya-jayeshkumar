1.1 Problem statement

The client needs a professional website where people can learn about the doctor's Ayurvedic knowledge, treatments, wellness information, and published content. Currently, without a content management system, the client may have to depend on a developer whenever new information or images need to be added.

The proposed system will provide a public website and an easy-to-use admin dashboard. The doctor can manage content independently without writing code, while visitors can access published information from mobile phones or computers.

1.2 Project objectives

Establish a professional online presence for the doctor.

Display the doctor's name, profile, qualifications, clinic address, contact information, and timings.

Publish Ayurvedic blogs, articles, treatments, points, and images.

Allow the doctor to create, edit, delete, and publish content without developer assistance.

Make published content publicly accessible through shareable URLs.

Provide a responsive, mobile-friendly interface.

Protect admin access and uploaded content.

Make the website easy to maintain and expand in the future.

3. Non-functional requirements

Security: Admin-only operations must be protected by server-side authorization.

Performance: Images should be compressed and pages should load efficiently.

Usability: The doctor should be able to publish an article without technical knowledge.

Availability: The website should remain accessible subject to the hosting provider's uptime and free-tier limits.

Maintainability: Frontend, backend, database, and image storage should be organized separately.

Accessibility: Use readable fonts, adequate contrast, descriptive image alt text, and keyboard-accessible controls.

SEO: Each article should have a descriptive URL, page title, meta description, and shareable preview.

Privacy: Only necessary information should be collected. Any patient information or sensitive medical records should be outside the initial project scope.

4. Recommended technology stack

For this project, I recommend a custom full-stack application because the client wants to manage content himself.

*Frontend — React + Vite

Builds the public pages, article pages, admin dashboard, content forms, and responsive interface.

Additional tools: React Router, Axios, CSS or Tailwind CSS.
*Backend — Node.js + Express

Handles login, authorization, article CRUD operations, image upload requests, and API endpoints.

Additional tools: express-validator or Zod, bcrypt, and an authentication library.
*Database — MySQL

Stores admin credentials, doctor profile information, articles, categories, image URLs, and publication timestamps.
*Image storage — Cloudinary or equivalent

Stores article images and returns image URLs. The database stores those URLs, not the image files themselves.
*Development tools — Git and GitHub

Version control, source code backup, and deployment integration.

5.1 Public content flow

A visitor opens the website.

React requests published content from the backend.

Express queries MySQL for published posts.

MySQL returns the article data.

React renders the content and loads images from image storage.

5.2 Admin publishing flow

The doctor opens the admin login page.

The backend verifies the login credentials.

The doctor opens the content editor.

The doctor enters a title, article, category, and images.

Images are uploaded to the image storage service.

The backend validates the content and saves it in MySQL.

The post status becomes PUBLISHED.

The public website fetches the new post and displays it.

No frontend redeployment should be needed when the doctor publishes a new article

9. Backend API design

The frontend and backend communicate through REST API endpoints.

Use a versioned API prefix: /api/v1.

9.1 Public endpoints

Method	Endpoint			Purpose
GET	/api/v1/profile			Fetch doctor information
GET	/api/v1/categories		Fetch public categories
GET	/api/v1/posts			List published posts
GET	/api/v1/posts/:slug		Fetch one published article
GET	/api/v1/posts/featured		Fetch featured posts, if implemented

The posts listing endpoint should support pagination and optional filters such as category and search term.

Example:

GET /api/v1/posts?page=1&limit=9&category=blogs&search=herbs

Only PUBLISHED posts should be returned by public endpoints.

9.2 Admin endpoints

Method	Endpoint				Purpose
POST	/api/v1/admin/auth/login		Authenticate admin
POST	/api/v1/admin/auth/logout		End session
GET	/api/v1/admin/auth/me			Check current admin session
GET	/api/v1/admin/posts			List all posts, including drafts
POST	/api/v1/admin/posts			Create a post
PATCH	/api/v1/admin/posts/:id			Edit a post
DELETE	/api/v1/admin/posts/:id			Delete a post
POST	/api/v1/admin/uploads			Upload an image
PATCH	/api/v1/admin/profile			Update doctor profile
POST	/api/v1/admin/categories		Create a category
PATCH	/api/v1/admin/categories/:id		Edit a category
DELETE	/api/v1/admin/categories/:id		Delete an unused category

For immediate publishing, the create/update request should accept a publish action and save status = PUBLISHED with published_at set to the current time. Editing an already published post should update the public content without requiring a new deployment.

Do not allow deleting a category while posts still reference it; either block the operation or require those posts to be reassigned first.

10. Authentication and security

The admin panel is private, but the public website is open to everyone.

Recommended login approach

Create the admin account during setup using a secure seed script or one-time setup procedure.

Store only a strong password hash, never a plain-text password.

Use bcrypt or Argon2 for password hashing.

After successful login, issue a secure session or authentication token.

Protect all admin API routes with authentication middleware.

Validate the admin's permissions on the server for every create, update, delete, and upload operation.

Add logout and session expiration.

Configure HTTPS and secure cookie settings in production.

For a single-admin website, an HTTP-only, Secure, SameSite cookie-based session is a good option. If you use cookie authentication, configure CSRF protections where applicable. Never put a permanent admin secret in frontend code or commit passwords to GitHub.

Additional security requirements

Rate-limit login attempts.

Validate title, slug, category, and article content on the backend.

Limit upload size and accept only allowed image types.

Check actual file content instead of trusting the filename extension alone.

Sanitize article HTML if using a rich-text editor to prevent cross-site scripting (XSS).

Keep database credentials and cloud-storage credentials in environment variables.

Use restricted database permissions and automated backups where available.

Do not expose unpublished posts through public API endpoints.

Avoid collecting patient medical records unless separately specified and properly secured.

Important distinction

Visitors do not need an account to read articles. Only the doctor needs an admin account to manage website content.

11. Image storage and article editor

The client needs to upload images with blogs and Ayurvedic articles. Therefore, image handling must be part of the initial implementation.

Recommended approach

Use a cloud image service such as Cloudinary, or an equivalent service with a suitable free tier.

Step 1 — Upload

The admin selects an image in the editor. The frontend sends it to the authenticated backend upload endpoint.

Step 2 — Validate

The backend checks the user's authorization, file size, and allowed image format before forwarding the upload.

Step 3 — Store

The image service stores the image and returns its URL. Keep upload credentials on the server.

Step 4 — Save

Save the URL in the post's cover_image_url column and reference it when displaying the article.

Article editor requirements

The admin editor should contain:

Title

Category

Short excerpt

Article content with headings, paragraphs, lists, and links

Cover image upload and preview

Optional additional inline images

Publish button

Edit and delete actions on the post list

For the first version, use a simple rich-text editor rather than building one from scratch. Sanitize its output on the backend, and limit image sizes to avoid slow pages.

When a post is deleted, handle its associated images safely. Avoid deleting an image that is still used by another post.

16. Medical content and legal considerations

Since this is an Ayurvedic information website, include the following safeguards:

Display accurate, doctor-approved qualifications and contact information.

Make it clear that educational content is not a substitute for individualized medical advice.

Avoid presenting unverified claims as proven cures or guaranteed treatment outcomes.

Have the doctor review articles about treatments, herbs, dosage, and potential risks before publication.

Do not add patient testimonials, photographs, or personal medical details without appropriate permission.

Include a privacy policy and explain how any information submitted through contact forms will be used.

Review applicable Indian laws and advertising requirements before publishing treatment claims or promoting products.

The admin panel should allow the doctor to publish immediately, but the client remains responsible for the accuracy and appropriateness of the content he publishes.
